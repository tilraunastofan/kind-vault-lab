# Kubernetes v1.37 features: what the lab uses and what it doesn't

The lab's kind cluster runs **v1.37.0**. Two upstream posts were reviewed:

| Post | Feature | Stage (per the post) | Lab verdict |
|---|---|---|---|
| [Pod Certificates and Cluster Trust Bundles](https://kubernetes.io/blog/2026/08/28/kubernetes-v1-37-pod-certificates-and-cluster-trust-bundles/) (2026-08-28) | `ClusterTrustBundle`, `PodCertificateRequest` | foundations GA in 1.37 | **ClusterTrustBundle adopted**; Pod Certificates noted as a future idea |
| [Pod-Level Resource Managers](https://kubernetes.io/blog/2026/09/15/kubernetes-v1-37-pod-level-resource-managers-beta/) (2026-09-15) | kubelet Topology/CPU/Memory managers honouring pod-level `.spec.resources` | Beta, **disabled by default** (`PodLevelResourceManagers` gate) | **Not applicable**; reasons below |

## 1. Cluster Trust Bundles: adopted

The change: the per-namespace `bao-ca` ConfigMaps (3 copies of OpenBao's lab CA) are replaced by **one cluster-scoped
ClusterTrustBundle**, mounted by pods through a `clusterTrustBundle` projected volume. Full write-up, YAML and
findings in `CLUSTER-TRUST.md`. Short version:

- Why it matters for OpenBao: pods reach OpenBao at `https://bao:8200`, signed by a private CA no image trusts.
  Trust distribution is now a cluster-level object with RBAC (`attest` on the signer) instead of a namespaced copy.
- Side effect: ClusterTrustBundle requires `CA:TRUE` on the CA, which exposed (and fixed) a missing
  `basicConstraints` in `scripts/bao-up.sh`.
- Not automatic: pods still opt in with the volume; nothing edits container trust stores.
- Pod Certificates (same post): needs a third-party signer in 1.37. Possible future lab item: a signer that
  forwards `PodCertificateRequest`s to OpenBao's PKI engine (`PKI.md`, `IDEAS.md`).

## 2. Pod-level resource managers: evaluated, not applicable

What the post describes: kubelet's Topology, CPU and Memory managers can use pod-level resource declarations
(`.spec.resources`) when making placement decisions. A latency-critical main container can get exclusive,
NUMA-aligned CPU/memory while non-Guaranteed sidecars (log agents, exporters) share a pod-isolated pool instead of
each needing whole dedicated cores. The v1 PodResources gRPC API gains top-level `cpu_ids` and `memory` fields.

Why it does not fit the lab, checked on the running cluster:

- **Disabled by default and a node feature:** it needs the `PodLevelResourceManagers` gate plus a kubelet configured
  with the static CPU manager / Topology Manager policies. Our kubelets set none of these (`cpuManagerPolicy` is
  unset in `/var/lib/kubelet/config.yaml`).
- **Nothing to align:** both kind nodes are containers in OrbStack's VM (10 CPUs, ~8 GiB each, shared host);
  NUMA placement on that is meaningless, and static CPU pinning would only waste a 16 GB laptop's capacity.
- **No sidecar-heavy pods:** lab pods are single-container; the only sized workload is Postgres, which uses plain
  container-level requests/limits (`k8s/data/postgres.yaml`).
- **No relation to OpenBao policy or trust:** the feature affects scheduling/performance, not identity or secrets.

When it would become relevant (production, not this lab): latency-sensitive workloads on NUMA hardware that also run
an OpenBao sidecar (Vault Agent injector, CSI/ESO helpers) or a mesh proxy. There the hybrid model lets the app have
exclusive cores while the secret-delivery sidecar shares a pooled allocation. Worth revisiting when the feature
reaches GA and is on by default.

What is available today without that gate: the pod-level `spec.resources` field itself is served by this cluster
(`kubectl explain pod.spec.resources`), if you want to experiment with pod-wide CPU/memory budgets for the lab's
multi-container test pods. Not adopted; nothing needs it yet.

## Where this leaves the lab
- Adopted: ClusterTrustBundle (`k8s/bao-ca/`, verified by `task smoke`).
- Candidate: OpenBao as the signer behind Pod Certificates (needs a small controller; not started).
- Parked: Pod-Level Resource Managers (re-evaluate at GA).
